# Dynamic ROSCA Database Schema

**Status:** Phase A, Task 1 — schema design  
**Scope:** Logical database design only. This document does not create tables, alter a database, or run migrations.

## 1. Design objectives

The database must support independently configured ROSCA circles without a fixed member count, collection-position count, contribution amount, or frequency.

The core hierarchy is:

**Branch → Circle configuration → Tenant → Tenant tenure**

- A branch is the community or organisation operating circles.
- A circle configuration defines the terms for a type of circle offered by a branch.
- A tenant is one instantiated circle created from exactly one configuration.
- A tenant tenure is one rotation of that tenant's members through the configured collection positions.
- A tenant can have successive tenures without overwriting earlier financial or operational history.

The configuration is the source of truth for new tenants. Financial and membership records must reference the tenant and tenure to which they belong.

## 2. Database conventions

- PostgreSQL.
- UUID primary keys generated by the database.
- TIMESTAMPTZ for instants. Schedule interpretation uses an explicit IANA timezone from the branch.
- Monetary amounts stored as integer minor units (BIGINT), never floating point. Currency is explicit (CHAR(3)).
- Rates stored as basis points (INTEGER): 200 = 2.00%; 150 = 1.50%.
- Use foreign keys and unique constraints for integrity; application validation alone is insufficient.
- Mutable records carry created_at and updated_at.
- Financial events and audit history are append-only. Corrections use reversals or compensating entries.
- No global CIRCLE_SIZE or global contribution amount determines a tenant's terms.

## 3. Core tables

### 3.1 users

One identity per person or platform operator.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| phone | TEXT | Required; unique in canonicalised form |
| email | CITEXT / TEXT | Nullable; unique when supplied |
| password_hash | TEXT | Nullable where authentication method permits |
| display_name | TEXT | Required |
| global_role | TEXT | Constrained platform role, e.g. USER, SUPER_ADMIN |
| account_status | TEXT | ACTIVE, SUSPENDED, CLOSED |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Branch-level roles belong in branch_memberships, not in a single global role field.

### 3.2 branches

One community/organisation workspace.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| name | TEXT | Required |
| slug | TEXT | Unique public identifier |
| status | TEXT | ACTIVE, SUSPENDED, ARCHIVED |
| timezone | TEXT | IANA timezone used for schedules |
| created_by_user_id | UUID | FK to users.id |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

### 3.3 branch_memberships

Associates users with branches and their branch-specific roles.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| branch_id | UUID | FK to branches.id |
| user_id | UUID | FK to users.id |
| role | TEXT | e.g. BRANCH_ADMIN, BRANCH_OPERATOR |
| status | TEXT | INVITED, ACTIVE, SUSPENDED, REMOVED |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraint: UNIQUE (branch_id, user_id). A user may administer multiple branches; a branch may have multiple authorised operators.

### 3.4 circle_configurations

An immutable set of terms created by a branch administrator.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| branch_id | UUID | FK to branches.id |
| created_by_user_id | UUID | FK to users.id |
| name | TEXT | Required configuration label |
| contribution_amount_minor | BIGINT | Positive amount per member per period |
| currency | CHAR(3) | ISO 4217 currency code |
| contribution_frequency | TEXT | WEEKLY or MONTHLY |
| max_co_savers | INTEGER | Positive configured capacity; no fixed 12 |
| collection_positions | INTEGER | Positive; equals max_co_savers for one payout per co-saver |
| tvc_annual_rate_bps | INTEGER | Financial-policy snapshot; 200 represents 2% |
| platform_fee_bps | INTEGER | Financial-policy snapshot; 150 represents 1.5% |
| status | TEXT | ACTIVE, INACTIVE, ARCHIVED |
| created_at | TIMESTAMPTZ | Creation timestamp |

Constraints and rules:

- max_co_savers > 0.
- collection_positions > 0.
- collection_positions = max_co_savers for the agreed one-payout-per-member model.
- contribution_amount_minor > 0.
- contribution_frequency IN ('WEEKLY', 'MONTHLY').
- UNIQUE (id, branch_id) supports composite branch-consistency foreign keys.
- Financial terms cannot be edited or deleted after creation. A changed term set is a new configuration. Status changes do not rewrite terms.
- Do not store a redundant duration value: the number of collection periods is derived from collection_positions; calendar dates are derived from the actual schedule.

### 3.5 tenants

One instantiated circle using one configuration.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| branch_id | UUID | FK to branch |
| configuration_id | UUID | FK to configuration, same branch |
| sequence_number | BIGINT | Sequence within this configuration |
| public_reference | TEXT | Unique externally safe identifier |
| status | TEXT | FILLING, AWAITING_VERIFICATION, ACTIVE, COMPLETED, SUSPENDED, CANCELLED |
| activated_at | TIMESTAMPTZ | Null until activation |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraints and rules:

- Composite FK (configuration_id, branch_id) references circle_configurations(id, branch_id), preventing cross-branch configuration use.
- UNIQUE (configuration_id, sequence_number) makes each configuration's tenant sequence independent.
- Capacity and terms are read from the immutable configuration. If operational snapshots are required, capture them at tenant creation; never use environment defaults.
- Tenant creation and sequence allocation must be transactional and concurrency-safe.

### 3.6 tenant_members

Membership and assigned collection position for a tenant.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| tenant_id | UUID | FK to tenants.id |
| user_id | UUID | FK to users.id |
| position_number | INTEGER | 1 through configured collection_positions |
| membership_status | TEXT | PENDING, ONBOARDED, VERIFIED, WITHDRAWN, REMOVED |
| joined_at | TIMESTAMPTZ | Join timestamp |
| verified_at | TIMESTAMPTZ | Null until verification |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraints and rules:

- UNIQUE (tenant_id, user_id) prevents duplicate membership.
- UNIQUE (tenant_id, position_number) prevents duplicate position allocation.
- Position must be positive and no greater than the tenant configuration's collection_positions. Enforce using transaction-safe logic or a narrowly scoped trigger because a normal CHECK constraint cannot read another table.
- Member count must never exceed configured capacity.
- Allocation of the final position must be protected against concurrent joins.

### 3.7 tenant_tenures

One rotation/round of collection positions for a tenant. This preserves earlier completed rotations when a tenant renews.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| tenant_id | UUID | FK to tenants.id |
| tenure_number | INTEGER | Starts at 1; increments per tenant |
| status | TEXT | PENDING, ACTIVE, COMPLETED, CANCELLED |
| activated_at | TIMESTAMPTZ | Actual start timestamp |
| completed_at | TIMESTAMPTZ | Null until completion |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraint: UNIQUE (tenant_id, tenure_number). Enforce only one active tenure per tenant with a partial unique index. Renewal creates a new row; it never overwrites prior contributions, periods, payouts, or ledger history.

## 4. Operational and financial tables

### 4.1 contribution_periods

One scheduled contribution/collection period for a tenure.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| tenure_id | UUID | FK to tenant_tenures.id |
| period_number | INTEGER | 1 through configured collection_positions |
| due_at | TIMESTAMPTZ | Scheduled due instant |
| status | TEXT | SCHEDULED, OPEN, COMPLETED, CANCELLED |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraint: UNIQUE (tenure_id, period_number). Dates are generated from activation and configuration frequency, not tenant creation time.

### 4.2 contributions

A member's contribution for a particular period.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| tenure_id | UUID | FK to tenant_tenures.id |
| period_id | UUID | FK to contribution_periods.id |
| tenant_member_id | UUID | FK to tenant_members.id |
| amount_minor | BIGINT | Positive amount |
| currency | CHAR(3) | Explicit currency |
| status | TEXT | PENDING, RECEIVED, FAILED, REVERSED, RECONCILED |
| payment_reference | TEXT | External payment reference; unique where supplied |
| received_at | TIMESTAMPTZ | Null until received |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraint: UNIQUE (period_id, tenant_member_id) prevents duplicate contribution records for the same member and period. Period and member must belong to the same tenant/tenure; enforce with composite keys or transactional consistency checks.

### 4.3 payout_intents

A payout request for one member's collection position in one tenure.

| Column | Type | Rules / purpose |
|---|---|---|
| id | UUID | Primary key |
| tenure_id | UUID | FK to tenant_tenures.id |
| tenant_member_id | UUID | FK to tenant_members.id |
| collection_position | INTEGER | The member's configured position |
| gross_amount_minor | BIGINT | Gross pool amount |
| tvc_adjustment_minor | BIGINT | Signed TVC adjustment |
| pot_after_tvc_minor | BIGINT | Gross amount plus/minus TVC |
| platform_fee_minor | BIGINT | Fee applied after TVC |
| net_amount_minor | BIGINT | Final amount payable |
| currency | CHAR(3) | Explicit currency |
| status | TEXT | PENDING, APPROVED, PAID, FAILED, REVERSED |
| payment_reference | TEXT | External payout reference |
| confirmed_at | TIMESTAMPTZ | Null until confirmed |
| created_at, updated_at | TIMESTAMPTZ | Audit timestamps |

Constraint: UNIQUE (tenure_id, collection_position) prevents duplicate payouts for a position in a tenure. Persist each calculation component to preserve the calculation actually applied if financial policy changes later.

### 4.4 ledger_transactions and ledger_entries

Append-only financial audit journal. The platform records and reconciles activity; it does not custody or hold the ROSCA pool.

**ledger_transactions:** transaction ID, branch ID, tenant ID, tenure ID, event type, source record type/ID, idempotency key, description, occurred timestamp, created timestamp.

**ledger_entries:** entry ID, transaction ID, account code/reference, debit amount, credit amount, currency, created timestamp.

Rules:

- Each posted transaction balances debits and credits per currency.
- Debit/credit values are non-negative integer minor units; an entry cannot have both debit and credit positive.
- Posted entries cannot be edited or deleted.
- Corrections use reversal transactions.
- Idempotency keys are unique within the relevant event scope.
- Journal references identify actual external accounts or account references; they must not imply that the platform holds customer funds.

### 4.5 pool_accounts

References designated bank/payment accounts controlled by the branch administrator.

Columns: id, branch_id, optional tenant_id, account holder name, provider/bank name, masked account identifier, currency, status, verification metadata, created_at, updated_at.

Store only account information needed by the application. Do not store online banking credentials or full card data. Tenant-specific account references must belong to the same branch.

### 4.6 kyc_records

Member verification submissions and outcomes.

Columns: id, user_id, optional tenant_id, verification provider/reference, status, submitted_at, reviewed_at, reviewer_user_id, rejection reason code, metadata reference, created_at, updated_at.

Keep sensitive identity documents in approved object storage with access controls; store references and minimal metadata in PostgreSQL. A tenant cannot activate until every required member is verified.

### 4.7 receipts

Proof of contribution or payout.

Columns: id, tenant_id, tenure_id, optional contribution_id, optional payout_intent_id, uploaded_by_user_id, object-storage key, content type, file size, checksum, status, created_at.

A receipt must reference the correct tenant/tenure and exactly one supported financial event.

### 4.8 notifications

Delivery and read state for user notifications.

Columns: id, user_id, optional branch_id, optional tenant_id, optional tenure_id, event_type, payload, channel, delivery_status, sent_at, read_at, created_at.

Notification content is generated from actual configuration/tenant values; no fixed member-count wording.

### 4.9 audit_events

Security and business audit trail.

Columns: id, actor_user_id, branch_id, entity_type, entity_id, action, before/after JSON snapshots where appropriate, request_id, IP metadata subject to retention policy, occurred_at.

Use for sensitive administrative actions, configuration creation/archival, membership changes, verification decisions, and financial lifecycle transitions. Do not put secrets or raw identity documents in audit payloads.

## 5. Essential indexes and uniqueness

At minimum:

- UNIQUE branch_memberships (branch_id, user_id).
- circle_configurations (branch_id, status, created_at).
- UNIQUE tenants (configuration_id, sequence_number).
- tenants (branch_id, status, created_at).
- UNIQUE tenant_members (tenant_id, position_number).
- UNIQUE tenant_members (tenant_id, user_id).
- UNIQUE tenant_tenures (tenant_id, tenure_number).
- Partial unique index for one active tenure per tenant.
- UNIQUE contribution_periods (tenure_id, period_number).
- UNIQUE contributions (period_id, tenant_member_id).
- UNIQUE payout_intents (tenure_id, collection_position).
- Unique ledger idempotency key in its defined scope.
- Index foreign-key columns used in joins and lookups.

## 6. Dynamic-capacity integrity

The database must not encode a circle size in a CHECK constraint or default.

Configured capacity is obtained through tenant → circle_configuration.max_co_savers. The configured collection range is 1 through circle_configuration.collection_positions.

The schema enforces these invariants using immutable configuration rows, composite foreign keys, transaction-safe allocation, and narrowly scoped triggers where a cross-table invariant cannot be expressed declaratively.

A tenant's member count must never exceed its configured capacity. Positions must be unique and within the configured range. Position count must not be inferred from the number of rows currently present.

## 7. Lifecycle and consistency rules

1. Create a configuration under an authorised branch.
2. Create each tenant with a configuration ID and branch-consistent relationship.
3. Allocate member positions atomically, respecting configured capacity.
4. Do not activate a tenant until all configured positions are occupied and all required members are verified.
5. Create the first tenure and contribution periods from the actual activation timestamp.
6. Contributions and payouts must reference the correct tenure, period and member.
7. Complete a tenure only after all configured collection positions have been processed under payout rules.
8. Renewal creates a new tenant_tenures row; it does not erase or rewrite the prior tenure.
9. Create the next tenant sequence independently for the same configuration when provisioning rules require it.
10. Preserve financial history and use reversals for corrections.

## 8. Decisions deliberately not hard-coded here

- No universal maximum circle capacity is specified. Any upper safety limit must be an explicit product policy, not a fixed circle size.
- The maximum number of tenants per branch/admin is an account-level policy, separate from circle capacity.
- Branch timezone controls schedule interpretation; exact defaults and selection rules belong in configuration/API design.
- The exact monthly date rule (same calendar day, end-of-month clamping, daylight-saving handling) must be fixed in the scheduling task before migration implementation.
- The precise TVC period conversion and rounding rule must be fixed in the TVC implementation task. Payout rows persist the applied calculation components.
- Whether member positions remain fixed across successive tenures is a product rule to confirm during tenant/renewal implementation. The schema preserves each tenure independently so the decision does not destroy history.

## 9. Next implementation step

After this logical model is reviewed, translate it into numbered PostgreSQL migrations, then add database-level integrity constraints and indexes. Repository/services and lifecycle tests follow the migration work.
